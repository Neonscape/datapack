# 游戏数据包与表格需求说明 v0.2

> v0.2 将数据包明确为由工程文件管理的受限 CUE 表格工程，并确定逻辑命名空间、工具配置分区、单元格公式、两轮校验和安全写入规则。

## 1. 目标

用一套统一的数据包，替代“xlsx 配表 + 手工导表 + 多份导出文件”的工作流。

这套数据包需要满足：

- 表格源文件是唯一可信的数据来源，不再以 xlsx 作为正式数据。
- 策划可以在接近 Excel 的表格界面中维护数据，不需要手写数据文件。
- 数据结构、填写规则、编辑器显示信息和导出配置放在同一张表的源文件中。
- 填错数据时，能明确指出哪一行、哪一列错了，以及原因。
- 导出数据只能来自通过校验的表，避免错误数据进入游戏。
- 源文件是文本，便于版本管理、查看修改内容和处理多人合并。
- 编辑器只管理本格式生成的受限 CUE 文件，不以打开任意合法 CUE 文件为目标。

## 2. 基本概念

### 数据包

一个数据包是一组相互关联的游戏数据表，以及它们共用的规则定义和导出产物。

例如，一个 RPG 项目的数据包可以包含：

- 道具表
- 效果表
- 怪物表
- 技能表
- 掉落表
- 通用规则定义

数据包中的表可以通过外键保持连接。例如，道具表中的 `effectId` 列可以声明外键约束，要求其中填写的 ID 必须存在于效果表。

### 数据表

一张表描述一类同结构的数据。

例如“道具表”的每一行是一件道具，包含 ID、名称、价格、稀有度和效果 ID 等列。

每张表都应同时包含：

- 表的基本信息
- 主键规则
- 列定义与填写约束
- 实际行数据
- 编辑器显示信息
- 导出配置

### 主键

主键是每行的唯一 ID，例如 `sword_001`。

- 主键在一张表内不能重复。
- 主键可以有命名规则，例如只能使用小写字母、数字和下划线，且必须以字母开头。
- 其他表可以通过外键引用这一行数据的主键。
- 修改或删除主键时，必须检查其他表是否仍在引用它。

## 3. 工程、文件格式与组织

### 工程文件

数据包根目录包含一个工程文件，作用类似解决方案文件。用户通过工程文件打开整个数据包，编辑器只管理该工程范围内的文件。

工程文件不逐一登记数千张表，而是声明：

- 工程格式版本
- 一个或多个表目录入口
- 一个或多个公共 Schema 入口
- 文件排除规则
- 导出配置，包括导出格式、导出视图和导出目录

工程文件使用 `.dtproj` 扩展名和 JSON 编码。其字段见 `dtproj-format-v1.md`。编辑器按照入口和排除规则自动发现表。

### 逻辑命名空间

每张表具有独立于文件路径的逻辑命名空间和表名，使用类似 C# namespace 的层级名称：

```text
combat.character.attack_growth
combat.effect
economy.item
```

约定：

- 工程内完整表名必须唯一。
- 表引用始终保存完整表名，不依赖文件相对路径。
- 物理目录可以按命名空间组织，但目录不是表身份的一部分。
- 移动物理文件不会改变表名和引用。
- 修改命名空间或表名属于重构操作，必须由编辑器统一更新所有引用。
- CUE 的 `package` 仍然一表一个，只负责隔离 CUE 求值，不承担逻辑命名空间功能。
- 为保证跨平台行为一致，命名空间、表名、目录名和字段名建议使用小写 ASCII、数字和下划线。

### 一表一目录，一表一源文件

每张表独占一个目录和一个源文件。

```text
tables/
    item/
        item.cue
    effect/
        effect.cue
    monster/
        monster.cue
```

约定：

- 表目录名、表源文件名和表内部名称建议保持一致或可明确对应，但表的正式身份由逻辑命名空间和表名决定。
- 一张表不能与其他表混放在同一个数据定义单元中。
- 表源文件是该表的唯一编辑来源。

这样做的目的，是让每张表独立、清楚，避免不同表的数据和规则互相影响。

### 数据包目录建议

```text
game-data/
    game-data.dtproj           # JSON 工程入口
    cue.mod/                  # 数据包的 CUE 模块信息
    tables/                   # 业务数据表
        item/
            item.cue
        effect/
            effect.cue
        monster/
            monster.cue
    schema/                   # 可跨表复用的规则定义
        common/
            common.cue
    exports/                  # 自动生成的导出文件，不作为源数据维护
        item.csv
        effect.csv
```

约定：

- `tables/` 是正式业务数据的来源。
- `schema/` 放跨多张表复用的规则，例如通用稀有度、非负整数、资源路径格式等。
- `exports/` 只放自动生成的结果，不应作为人工修改来源，也不应反过来覆盖表源文件。
- 数据包可以被校验、导出和构建流程统一识别。

## 4. 单表内容

一张表的源文件按固定顺序组织：

1. package 和公共 Schema 引用
2. 主键规则
3. 本表专用规则
4. 行结构定义
5. 行数据
6. 工具链信息
7. 编辑器信息
8. 导出配置

概念示例：

```cue
package item

#PrimaryKey: string & =~"^[a-z][a-z0-9_]*$"

_local: {
    #Price: int & >=0
    #Rarity: "N" | "R" | "SR" | "SSR"
}

#Row: {
    name:   string
    price:  _local.#Price
    rarity: _local.#Rarity
    effect: string
}

rows: {
    [ID=#PrimaryKey]: #Row

    sword_001: {
        name:   "Iron Sword"
        price:  100
        rarity: "N"
        effect: "burn_small"
    }
}

_tool: {
    version: 1
    table: {
        namespace: "economy"
        name:      "item"
    }
    foreignKeys: {
        effect: {table: "combat.effect"}
    }
    formulas: {}
}

_editor: {
    columns: {}
}

_export: {
    csv: {enabled: true}
}
```

### 各分区职责

| 分区 | 职责 |
|---|---|
| `#Row` | 最终行数据的字段、类型、必填、默认值、枚举、范围等规则；它是数据结构的唯一标准 |
| `rows` | 人工填写的固定值 |
| `_tool` | 格式版本、表身份、外键约束、单元格公式和其他工具链语义 |
| `_editor` | 标题、备注、顺序、列宽、控件等纯表现信息 |
| `_export` | 导出视图、字段选择、字段命名和编码方式 |

`_editor.columns` 只能辅助显示，不能重新定义 `#Row` 中的字段或类型。`_tool`、`_editor` 和 `_export` 的结构由核心程序内置的 CUE Schema 检查；目标表、字段和公式引用是否存在等关系由 Go 检查器检查。

表格式包含版本号。升级格式时由编辑器执行明确的迁移，不能在读取时静默猜测旧格式。

### 列类型

第一阶段支持适合普通表格编辑和 CSV 导出的扁平列：

- 文本
- 整数
- 小数
- 布尔值
- 枚举值
- 对其他表主键的引用
- 由原始值组成的数组，例如标签列表、效果 ID 列表
- 成员都是原始值的一层结构体，例如坐标、数值区间、属性加成

数组和结构体必须保持扁平：

- 数组元素只能是文本、数字、布尔值、枚举值或主键引用。
- 结构体成员只能是上述原始值，不能再包含数组或结构体。
- 不支持数组中放结构体，也不支持任意层级嵌套。

例如以下结构暂不作为普通列支持：

```cue
position: {
    points: [{x: 1, y: 2}]
}
```

复杂数据优先拆成独立表，再通过 ID 引用。

## 5. 规则与校验

### 表内规则

每一列可以定义填写规则，例如：

- 必填
- 文本、整数、小数、布尔值等类型要求
- 数值上下限
- 枚举可选值
- 文本格式，如 ID 命名规则

示例：

```cue
price: int & >=0
rarity: "N" | "R" | "SR" | "SSR"
```

### 本表规则和全局规则

规则分为两类：

- 本表规则：只服务当前表，例如道具价格必须非负。
- 全局规则：可被多张表复用，例如所有稀有度字段使用同一组枚举值。

全局规则是跨表基础规则。它的修改应和普通填表分开处理，因为一次修改可能影响许多表。

### 外键约束

外键是列的数据约束，用于保证表之间的连接有效。外键列中的非空最终值必须与目标表中的某个主键完全相等。

外键声明保存在 `_tool.foreignKeys` 中，例如：

```cue
_tool: {
    foreignKeys: {
        effectId: {table: "combat.effect"}
    }
}
```

它表示：

```text
economy.item.effectId 中填写的每个非空 ID，都必须存在于 combat.effect 的主键集合中。
```

第一阶段约定：

- 外键只能指向目标表的主键，目标表使用完整逻辑名称。
- 一个外键列只能指向一张目标表。
- 标量外键检查一个值；数组外键逐项检查，数组中的所有元素指向同一张目标表。
- 标量或数组的基数直接从 `#Row` 推导，不在 `_tool.foreignKeys` 中重复声明。
- 外键源值的类型必须与目标主键类型相同，不做字符串、整数等类型之间的隐式转换。
- `null` 表示缺失。若该列有默认值，先取得默认值再检查外键；没有默认值时，是否允许缺失由 `#Row` 决定。
- 空字符串是实际字符串值，不是缺失值，必须像其他值一样在目标表主键中存在。
- 数组外键中的每一项都必须单独检查和定位，例如 `effectIds[2]`。
- 目标表、目标主键或外键声明中的字段不存在时，必须报错。
- 外键只检查目标主键是否存在，不读取或复制目标行的其他字段，导出时仍然导出源字段中保存的 ID。
- 第一阶段不支持一个数组混合引用多张表；这类多态引用以后单独设计。

外键是业务规则，不是编辑器显示信息，因此不能定义在 `_editor` 中。编辑器可以为外键列提供目标主键选择器，但用户仍可输入并保存暂时不存在的 ID；该错误会阻止导出。

### 跨表取值

跨表取值是指读取另一张表某一行的普通字段，例如在公式中读取某个效果的伤害值。它与只检查 ID 是否存在的外键约束是两项不同能力。

第一阶段不支持跨表取值。公式只能读取本表单元格，也不能通过外键访问目标行。

### 删除和改名保护

- 修改主键时，应列出所有外键引用位置，并允许确认后一起更新。
- 删除被其他表引用的行时，默认阻止删除，并告诉用户哪些地方仍在使用它。
- 第一阶段不自动把引用清空，也不自动删除引用方的数据。

### 错误呈现

所有错误应统一为可定位的信息：

```text
行：sword_001
列：price
原因：必须大于或等于 0，当前值为 -10。
```

至少需要覆盖：

- 文件语法错误
- 主键不合法
- 类型不对
- 数值或文本规则不满足
- 必填字段缺失
- 枚举值不合法
- 外键引用不存在
- 导出配置引用了不存在的列

## 6. 编辑器需要提供的功能

### 日常填表

- 查看表列表并打开一张表。
- 像电子表格一样查看和编辑单元格。
- 添加、删除行。
- 修改主键。
- 批量复制和粘贴单元格。
- 撤销和重做。
- 自动保存修改。
- 单元格输入完成并确认后才提交、写盘和重载；输入过程中的临时文本不写入 CUE。
- 显示列标题、备注和类型提示。
- 在单元格或错误列表中显示错误；点击错误可跳到对应格子。

### 适合字段类型的输入方式

- 枚举列使用下拉选择。
- 布尔列使用明确的真/假输入方式。
- 外键列可以从目标表已有主键中选择。
- 普通文本和数字列按类型输入。
- 数组列使用专用的列表编辑方式，支持逐项增删、排序和粘贴；每项都单独校验。
- 一层结构体使用展开的字段编辑方式，例如把 `position.x`、`position.y`、`position.z` 展开编辑；它在逻辑上仍属于同一列。

### 表结构管理

- 新建表。
- 添加列。
- 删除列。
- 重命名列。
- 调整列顺序。
- 修改列备注、填写规则、是否导出和引用关系。
- 为普通值单元格设置、批量填充或移除公式。
- 修改表结构时，明确提示对已有数据的影响。

删除或重命名列时，应同步处理：

- 行数据中的对应字段
- 编辑器列信息
- 导出列列表
- 不再使用的本表规则
- 工具配置中的外键和公式目标、公式引用

### 浏览辅助

以下功能对日常使用很重要，但可以后续加入：

- 排序
- 筛选
- 搜索
- 显示引用关系
- 显示某个 ID 被哪些表、哪些行使用

## 7. 导出要求

### 导出前门禁

只要存在错误，数据表就不能导出。

导出前至少检查：

- 所有表内规则都满足。
- 必填字段完整。
- 主键合法。
- 枚举值合法。
- 所有外键约束都满足。
- 所有公式成功计算且不存在循环引用。
- 导出列存在。
- 不导出未明确支持的嵌套对象或数组。

### CSV 导出

第一阶段导出 CSV。

- 导出列顺序由表配置明确指定。
- 主键可以作为导出的 `id` 列写出，即使它在源数据中是行 key。
- 文本中的逗号、引号和换行必须按 CSV 规则处理。
- 整数、小数、布尔值、枚举和引用值按明确规则转换。
- 数组和一层结构体默认编码为紧凑 JSON，写入一个 CSV 单元格；后续可为指定结构体增加展开成多个 CSV 列的配置。
- 缺失值默认视为错误，除非该列明确允许为空。

导出文件是产物，不是源数据。它可以被游戏工程读取，也可以在构建时自动生成。

### 后续可扩展的导出形式

在 CSV 跑稳后，可以按游戏运行时需要增加：

- JSON
- 二进制表
- SQLite
- 代码生成的数据结构
- ID 到索引的映射文件

这些都不应改变“表源文件是唯一数据来源”的原则。

## 8. 单元格公式

公式属于某个具体的数据单元格，用于在预览、校验和导出时计算该单元格的最终值。不同单元格可以使用不同公式，编辑器可以提供批量填充来减少重复操作。

### 保存方式

公式保存在 `_tool.formulas`，计算结果不写入 `rows`：

```cue
_tool: {
    formulas: {
        level_01: {
            attack: "base_attack * 1.2"
        }
        level_10: {
            attack: "combat.growth.level_09.attack + 20"
        }
    }
}
```

一个单元格只能具有固定值或公式，不能同时存在：

- 设置公式时，编辑器删除 `rows` 中对应的固定值。
- 改为固定值时，编辑器删除对应公式。
- 文件中两者同时存在时，格式检查报错，不静默选择其中之一。

### 引用和计算

- 公式可以引用本表中的任意普通值单元格，也可以引用其他公式单元格。
- 当前行字段直接使用字段名，例如 `base_attack * 1.2`。
- 其他行使用稳定的完整地址 `命名空间.表名.行主键.字段路径`，例如 `combat.growth.level_09.attack`，不使用会受排序影响的 `A10` 地址。
- 第一阶段公式中的完整地址必须指向当前表；该限制禁止跨表取值，但保留了未来扩展所需的稳定语法。
- 第一阶段公式不能通过外键访问目标行。
- 外键字段不能设置公式，公式也不能读取外键字段或外键数组。
- 工具链从公式 AST 提取引用，建立依赖图并按依赖顺序求值。
- 点分命名空间按完整前缀解析，例如 `rpg.balance.item.row.attack`；静态字符串方括号写法也可用于完整地址。行主键和字段名必须是静态名称，动态表/环境访问及数组元素引用会明确报错，不能绕过依赖校验。
- AST 引用分析区分函数调用、命名空间根和 `let` 局部绑定；它们不因与列同名而成为额外单元格依赖。限定地址不覆盖当前行的同名普通列。
- 公式之间出现循环引用时直接报错，并定位涉及的单元格。
- 修改主键或字段名时，编辑器解析公式 AST 并统一更新引用，不能使用普通字符串替换。

### 默认值和最终数据

读取一个单元格时按以下顺序取得值：

1. 公式结果
2. `rows` 中的固定值
3. `#Row` 中可具体求值的 CUE 默认值
4. 都不存在则报告缺失

公式计算失败时不能回退到固定值或默认值。CUE 默认值会显示在预览中并写入导出结果，编辑器应将默认值与明确填写的固定值作视觉区分。

计算开始前保留所有公式目标，不向其中填入默认值。只有正常输入可使用默认值；公式必须等待其所有公式依赖成功，解析、函数、执行或依赖失败都会保留错误状态，不能把缺省值当成已计算结果。

### 支持范围

公式目标必须是最终类型为文本、整数、小数、布尔值或枚举的非外键普通值叶子：

- 顶层普通值可以设置公式。
- 一层结构体中的普通值成员在底层模型中可用 `stats.attack` 这样的字段路径表示；界面支持可以后置。
- 整个结构体、整个数组和数组元素不能设置公式。
- 数组元素也不能作为公式引用目标，避免增删和排序造成引用含义变化。
- 主键不能设置公式。

公式引擎使用 Go 库 `expr-lang/expr`。关闭全部内置函数后，只开放确定性的运算和函数白名单，例如基础算术、比较、逻辑、条件表达式、`abs`、`min`、`max`、`round`、`floor`、`ceil`、`clamp`、`pow` 和 `len`。禁止时间、随机数、文件、网络和任意外部函数，保证相同输入始终得到相同结果。

### 两轮校验

含公式的表使用两轮处理：

1. 解析源文件，读取 `#Row`、`rows` 和 `_tool`；此时只报告语法、格式结构等无法继续处理的错误。
2. 取得默认值、计算公式并在内存中构造最终 `rows`，再使用 CUE Go API 与 `#Row` 统一，检查必填、类型、范围、枚举等最终错误。

公式结果只存在于内存中的最终数据，不写回源文件。项目的 `vet` 命令负责完整流程；原生 `cue vet` 不理解外部公式，不能作为最终构建门禁。

## 9. 协作与版本管理要求

- 表源文件必须是文本文件。
- 输出格式必须稳定：未改内容不应因为一次保存而产生无关修改。
- 行数据按主键稳定排序。
- 行内字段按列定义的顺序稳定输出。
- 编辑器生成的元信息按固定顺序输出。
- 备注等需要长期保留的信息应使用明确的数据字段保存，而不是依赖任意位置的自由注释。
- 本格式不使用原生 CUE 注释保存长期信息，也不承诺支持编辑器不认识的任意 CUE 写法。
- 导出产物不作为需要人工合并的源文件维护。

多人同时修改同一张表时，版本管理工具应能自动合并大多数不重叠的行或字段修改；发生冲突时，冲突内容应仍然是可读的文本。

第一版不提供结构化自动合并。检测到 Git 冲突标记时，应明确报告文件存在未解决冲突并停止管理该文件，交由用户修复。

### 安全保存和外部修改

- 单文件保存使用同目录临时文件，生成、解析和检查成功后再原子替换正式文件。
- 主键或表名重构等多文件操作先在内存中生成全部结果并统一检查，再备份和逐个替换；任一步失败都回滚已经替换的文件。
- 跨表操作作为一个撤销单元；MVP 不要求重启后保留撤销历史。
- 第一版不主动监视或自动重载外部文件变化。用户需要重新打开工程以读取外部修改；文件写入前仍应检查文件摘要，避免覆盖外部修改。
- 文件解析失败时，从当前可求值的 AST 和数据索引中移除，但在表列表中保留“损坏文件”占位和明确错误，不能用旧内存内容覆盖磁盘文件。
- 目标表损坏时，引用错误应显示“目标表当前不可用”，不能误报为目标 ID 不存在。
- 不符合本格式支持子集的 CUE 文件应拒绝编辑，不能在下次保存时静默丢弃未知内容。

### 工程加载和索引

- 启动时扫描工程范围内的表名、表元信息和文件状态。
- 后台建立主键、外键、公式和正反向引用索引；用户打开的表优先加载。
- 索引可以按路径、修改状态和内容摘要缓存，但缓存只用于加速，删除后必须可以完整重建。
- 关系索引尚未建立完成时，应暂停删除保护、跨表改名等依赖完整索引的操作，避免漏检。

## 10. 最小可用版本

第一版只要实现以下闭环即可投入小范围试用：

1. 创建一张表。
2. 定义扁平列和基本填写规则。
3. 添加、删除、编辑行数据。
4. 自动保存源文件。
5. 明确显示表内错误。
6. 定义和检查标量外键与数组外键。
7. 为普通值单元格设置公式，计算后使用 CUE 校验。
8. 导出 CSV。
9. 导出前阻止错误数据通过。

以下内容可以后续再做：

- 复杂嵌套数据
- 多种导出视图
- 代码生成
- 全局规则的图形化编辑
- 复杂跨表规则
- 二进制导出
- 跨表公式
- 数组和整个结构体公式
- 结构化自动合并
